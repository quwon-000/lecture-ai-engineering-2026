## 宿題

<!-- 基礎・実装・発展のどれか1つに取り組めば完了です。 -->

- 取り組んだレベル：基礎
- やったこと（変更したファイル・設定・処理、または設計した取得方法）：
  - `app/config.py` の `RAG_TOP_K`（通常のベクトル検索で返す最大件数）を `5` から `2` に変更した
- 比較した質問と、固定した条件（モデル・対象資料など）：
  - 質問：`第2回の説明では、LoRAは何を固定し何を学習しますか？ QLoRAは何を加えますか？`
  - 固定条件：モデル `gemini-3.5-flash-lite`、
  - 対象資料 第1〜3回の本講義214ページ（`data/rag_data/index.sqlite3`）。

- 結果（変更前後の回答・根拠、`--trace`の出力、時間・トークン数・生成API推定費用など）：
  - 変更前（`RAG_TOP_K = 5`）：
    - 回答・根拠：正答。引用は「第2回・PDF p.51, p.52」。
    - `--trace`：`search_materials({'query': 'LoRA QLoRA 固定 学習'})` を1回呼び出し。
    - 時間：4.98 秒 / 入力 3,027 tokens / 出力 180 tokens / モデル応答 2 回 / 生成API推定費用 `$0.001358 USD`

  - 変更後（`RAG_TOP_K = 2`）：
    - 回答・根拠：正答。引用は「第2回・PDF p.51, p.52」（変更前と同じ根拠を維持）。
    - `--trace`：`search_materials({'query': 'LoRA QLoRA 固定 学習'})` を1回呼び出し（ツール名・引数・回数ともに同じ）。
    - 時間：3.73 秒 / 入力 1,740 tokens / 出力 218 tokens / モデル応答 2 回 / 生成API推定費用 `$0.001067 USD`

- 改善した例と、残る失敗・制約：
  - 改善した点：単一〜隣接ページに答えがある質問では、`RAG_TOP_K` を `5` → `2` に絞ることで不要な周辺ページ（p.60, p.47, p.61 等）が除外され、回答の正確さと引用根拠（p.51, p.52）を保ったまま、入力トークン数を約42.5%削減（3,027 → 1,740 tokens）、生成API推定費用を約21.4%削減（`$0.001358` → `$0.001067`）、応答時間を 1.25 秒短縮できた。
  
  - 残る失敗・制約：取得件数を2件に減らしたため、複数の話題・ページにまたがる質問では1回の検索で必要な根拠が揃わず、モデルによる追加の検索呼び出し（ツール呼び出し回数の増加と応答時間の悪化）や一部根拠（p.13）の取りこぼしが生じやすくなる。

- 気づき・疑問：
  `RAG_TOP_K` の調整は索引の再作成が不要で手軽に試せる一方、「1問あたりの入力トークン削減」と「複数根拠の網羅性（リコール）」のトレードオフに直結する。検索結果数が少ない場合でも、エージェントが `INSTRUCTIONS` に従い追加の検索語を考えて再検索する振る舞いが `--trace` から確認できた。ただし再検索が増えると、かえって時間とモデル応答回数が増えるため、用途に応じた `RAG_TOP_K` のバランス調整が重要だと分かった。
